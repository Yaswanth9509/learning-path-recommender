Prerequisite-ordered learning paths, explained.

Recommending relevant courses is easy, and it is not the problem. Learners get stuck on sequence. This system generates a roadmap from a prerequisite graph and a topological sort, so an item can never be scheduled before the things it depends on — a property asserted in the test suite for every goal and every learner shape.

01

Problem understanding

What is actually broken, and for whom

Online platforms already solve retrieval. Search "machine learning" and thousands of credible courses come back, ranked by rating and popularity. A learner who wants to become an ML engineer is not short of relevant material — they are short of an order to consume it in.

That gap has a specific shape. Relevance is a property of a single item against a query. A learning path is a property of a set of items against a dependency structure: Deep Learning is relevant to the goal and useless as a first step, because it rests on linear algebra, Python, and classical ML that the learner may or may not already hold. A ranking function cannot express that constraint, so platforms leave the sequencing to the learner — precisely the judgement a newcomer to the field is least equipped to make.

The reframe this project is built on: a personalised learning path is not a ranked list. It is a topological ordering of a dependency graph, filtered by what this individual already knows and fitted to the time they actually have.

Four things vary between learners, and all four change the answer:

  • Starting point. Two people with the same goal need different paths because they arrive holding different skills — and a declared skill implies everything beneath it.
  • Objective. "Work with data" describes at least three careers whose first six months diverge sharply.
  • Capacity. Six hours a week and twenty hours a week produce the same ordering and completely different schedules.
  • Preference and response. Format, cost, difficulty — and how the learner reacts once material is in front of them.

A one-size answer fails all four. The system therefore has to model the learner, not just the catalogue.

02

Solution approach

From a sentence to an ordered roadmap

The learner types a goal in plain language. Six stages turn it into a roadmap, each one a pure function of the stage before it.

StageInput → outputMethod
Interpret Free text → goal id, level, weekly hours, known skills, format preferences LLM structured extraction, with a deterministic keyword engine underneath
Clarify Ambiguous text → a question, not a guess Relative-ambiguity test over goal match scores
Profile Declared skills → declared plus implied skills Transitive closure over the prerequisite graph
Analyse the gap Goal + profile → the skills still missing closure(goal targets) − known
Generate Missing skills → milestones of courses, projects, assessments Layered topological sort, then greedy multi-skill cover per layer
Explain & adapt Roadmap → rationale, and a rebuilt roadmap on new evidence Weighted scoring components reused as natural-language reasons

Why implied skills matter

A learner who says "I know deep learning" is never sent back to learn Python. Profiling walks the graph downward from every declared skill and credits the whole subtree, so the gap contains only genuinely missing material. This is one line of graph work that removes an entire class of insulting recommendation.

Milestones, not a flat list

A 445-hour ordered list is technically correct and psychologically useless. Selected courses are chunked into three to six milestones along dependency boundaries, and each milestone is capped with a project that exercises what it taught and an assessment that proves it. Every milestone carries hours, estimated weeks, and a cumulative week number, so the roadmap answers "when" as well as "what".

Honest failure

If the only course teaching a skill has been excluded by learner feedback, that skill and everything downstream of it is reported as uncovered rather than quietly scheduled anyway. Promising a course whose prerequisite the path never teaches would be a worse answer than admitting the gap.

04

AI/ML techniques used

Where the intelligence actually lives

The system combines four techniques. The choice worth defending is what is not here: there is no trained collaborative-filtering model, and that is deliberate.

Graph algorithms — the core

  • Transitive closure over the prerequisite DAG, in both directions: downward from the goal to compute everything required, and downward from declared skills to credit everything implied.
  • Kahn's algorithm for cycle detection, run at import over all 122 skills. A cycle makes any ordering impossible, so it fails loudly at startup rather than silently at generation.
  • Layered topological sort — not a single linear order, but dependency levels, so items that could be studied in parallel are grouped and can be scheduled together in one milestone.
  • Greedy set cover per layer: a course teaching three outstanding skills covers all three, so a learner is never sent to two courses where one would do.

Multi-criteria scoring — explainable by construction

Every candidate item is scored as a weighted sum of five components, each computed independently and all returned to the client.

ComponentWeightMeasures
goal_relevance0.37Share of the item's value landing on skills still missing
skill_readiness0.21Share of its prerequisites already held
level_fit0.16Distance from the difficulty target, adjusted by feedback
interest_match0.16Domain overlap with stated interests
format_fit0.10Format, cost, and provider preference

The same numbers that produce the ranking generate the human-readable reasons, so "why was this recommended?" always has a precise, checkable answer rather than a plausible-sounding one. The UI exposes the full breakdown, weight by weight, for any item.

Natural-language understanding — hybrid, with the model on the outside

Goal interpretation and question answering are implemented twice. A configured provider (Anthropic, Gemini, Groq, OpenRouter, or a local Ollama model) performs structured extraction against a JSON schema. Underneath sits a deterministic engine using keyword scoring, regex extraction for hours, and phrase detection for declared skills.

Everything a model returns is treated as untrusted: unknown goal and skill ids are discarded, out-of-range hours rejected, invalid levels and formats filtered, and JSON recovered from markdown fences or surrounding prose. Any failure — no credential, network error, rate limit, refusal, malformed output — degrades to the rule engine rather than surfacing an error. The LLM improves how the goal is read and how replies sound; it is never on the correctness path.

Ambiguity is handled by a relative test rather than an absolute confidence floor: the assistant asks a clarifying question when nothing matches or when a runner-up goal scores within 70% of the leader, and offers the distinguishable readings as one-click replies.

Behavioural estimation

Every learner overestimates their available hours. The progress table records when each item changed state, so the real rate is measurable: completed hours over elapsed weeks, compared against the planned figure. Below seven days of history it reports unknown rather than inventing a trend; beyond that it reports ahead, on track, or behind, and offers to refit the schedule.

Why no trained recommender? Collaborative filtering needs interaction data this system does not have on day one, and even with it, a learned ranking cannot express "B requires A" — it can only observe that people who took A often took B. That correlation collapses exactly where learners need help most: rare goals and unusual starting points. The graph encodes the constraint directly and is auditable by a human. With real interaction data, the natural place for a learned model is re-ranking within a dependency layer — choosing between three courses that are all valid next steps — which is additive to this design rather than a replacement for it.

Primary workflow

state a goal ──▶ interpreted (or clarified) ──▶ profile built ──▶ gap computed
                                                                      │
              roadmap ◀── milestones ◀── greedy cover ◀── topological layers
                 │
                 ├─▶ mark progress ─────────▶ dashboard updates, plan unchanged
                 ├─▶ give feedback ─────────▶ path rebuilt around the change
                 └─▶ re-plan to real pace ──▶ schedule refitted to observed hours

The split in that last group is deliberate. Ticking a box never reshuffles a learner's plan — a roadmap that moves underneath you is worse than a slightly stale one. Feedback and an explicit re-plan request both do trigger regeneration, because the learner asked for change.

Built beyond the brief

  • Accounts, guests and isolation. Register, sign in, or start as a guest with no email at all. A guest is a real account with a throwaway identity, so work is saved from the first message, and it can be upgraded to a permanent account in place — the user id never changes, so every learner, path and completed item stays exactly where it is. Each account sees only its own learners, and cannot read another's even by id.
  • Several goals at once. A learner runs up to three roadmaps side by side with one active, switchable from the Path tab and compared on the dashboard. Real people do not stop wanting one thing when they start wanting another.
  • The assistant asks before it assumes. Experience level and weekly hours decide where a path starts and how long it runs, so they are asked for once, up front, rather than defaulted silently. Answer "you decide" and it chooses — and says which numbers it chose, so they can be corrected.
  • A visible engine switch. The header names which engine will answer the next message, and every reply says which one produced it. When a free-tier key runs out of quota the app degrades to the rule engine and keeps working; without this you can be reading rule-engine output and concluding the model is bad.
  • Two storage engines behind one interface. The application is written against SQLite and stays that way; setting DATABASE_URL sends the identical SQL to Postgres instead. A deployment needs it, because a free instance has no persistent disk and would erase every registered account each time it sleeps.
  • Interactive skill graph. The actual prerequisite DAG rendered as an SVG in dependency columns. Every arrow is a constraint the planner obeyed; a test asserts each edge points strictly forward, so the drawing can never contradict the plan.
  • Weekly plan. The remaining roadmap poured into fixed-capacity weeks, splitting long courses across them: "week 3 — wrap up Modern JavaScript, start Data Structures".
  • Achievements. XP, seven levels, and nine badges tied to real milestones. Unearned badges show what would earn them.
  • Markdown export. The whole roadmap as a shareable document with checkboxes and per-item rationale.
  • Reference resources. Fifteen canonical links (MDN, the Python tutorial, Pro Git, the RAG paper) that are recommendable but never scheduled — path coverage is only ever satisfied by a course.
  • Prior learning history. Tick what you finished before this app existed; those completions leave the gap and survive every rebuild.

Challenges faced

The decisions that were not obvious

An unfillable gap in the middle of a path

When learner feedback excludes the only course teaching a skill, the naive options are both bad: schedule it anyway, or drop that skill and leave later items with unmet prerequisites. The resolution was to propagate — the skill and its entire downstream cone are reported as uncovered, and the path is generated around them. The learner sees an honest "no available course covers X" instead of a roadmap that quietly cannot work.

Completed work vanishing on rebuild

Finishing a course removes its skill from the gap, so the next rebuild correctly drops that course from the plan — and the learner's completed work disappeared with it. Progress and plan had to be decoupled: the dashboard counts every completion regardless of whether the item is still on the current path.

A second, subtler version of the same bug appeared when prior learning history was added. The routine that syncs completions treated the progress table as the only source of truth and overwrote everything else, silently erasing courses a learner had declared as already finished. It now gives the progress table ownership only of the items it actually tracks; declared history is preserved. Both directions are covered by tests.

Staying useful with no API key

Requiring a paid credential to see the product work would have made it unreviewable. Every AI-backed feature was therefore implemented twice, and the rule-based version had to be genuinely good rather than a stub — it varies phrasing, names the learner, and cites their actual stage and progress. The variation is seeded from the input rather than randomness, so it stays fully deterministic and testable.

Determinism versus useful variation

Identical inputs must produce an identical path, or the invariant tests cannot exist. That meant every tie broken by an explicit sort key rather than dict or set ordering — a constraint that touched course selection, milestone chunking, and support-item choice.

"Adapt to progress" versus a stable plan

The brief asks the system to adapt to progress; usability argues that a plan must not move under the learner. Resolved by separating them: progress updates mutate status in place, while an explicit re-plan action refits the schedule to the measured pace. The learner keeps a stable plan and gets adaptation when they ask for it.

Treating model output as hostile

Early on, a provider returned a confident goal id that did not exist in the catalogue. Everything crossing the model boundary is now validated against the catalogue and clamped to legal ranges, with recovery for JSON wrapped in prose or fences. The failure mode is always degradation to the rule engine, never an error surfaced to the learner.

How we know it works

Validation strategy

534 tests run in about half a minute with no network, no API key, and no tokens spent, at 90% branch coverage. The database is pinned to SQLite for the same reason the model is disabled: a configured DATABASE_URL must never send a test run to a real server. The load-bearing one is assert_prerequisites_respected: it walks a generated path in the exact order a learner would, accumulating taught skills, and fails if any item is ever reached before the skills it requires. It runs across all fourteen goals and three experience levels.

Limitations and next steps

Stated plainly
  • The catalogue is curated, not integrated. 183 items, each pointing at a real free resource — MIT OpenCourseWare, OpenStax, Khan Academy, MDN, official documentation — verified reachable before it shipped. What is curated is the selection: a human chose which resource teaches which skill, where a production system would ingest a provider feed and map it automatically. That is a data-layer change, not an architectural one.
  • Email deliverability is not guaranteed. A forgotten password is reset by single-use emailed link, sent through Brevo's HTTPS API on its free tier. The sender is a free-provider address, which cannot be DKIM-signed as itself, so some mail will land in spam until a domain is authenticated — a DNS change, not a code change. There is still no address verification at sign-up.
  • One connection, serialised. Every query goes through a single connection behind a lock — correct and simple for one process, and enough for a demo, but a busy deployment would want a pool. The seam is one module, so that is a contained change.
  • Rate limiting is in-process. Correct for one process; a multi-replica deployment would need a shared store.
  • Pace uses completion timestamps only. It cannot yet distinguish "studied five hours on Sunday" from "an hour a day", and does not model format-specific drop-off — the next honest signal to add.
  • No learned re-ranking. With real interaction data, a model choosing between equally valid next steps within a dependency layer is the natural extension.

Running it

Two commands, no credentials
pip install -r requirements.txt
python run.py                      # http://127.0.0.1:8000

# tests and lint
pip install -r requirements-dev.txt
python -m pytest                   # 534 tests, offline
python -m ruff check .

# or containerised
docker build -t rungs .
docker run -p 8000:8000 -v lpr-data:/data rungs

No API key is required. To make the assistant's replies conversational, copy .env.example to .env and set any one provider key — Gemini, Groq and Ollama all have free options, and Ollama runs locally with no network at all. Interactive API documentation is at /docs while the server runs.
